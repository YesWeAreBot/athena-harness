# 01 · 上下文构造

> Cortex 开发者参考手册。描述"上下文怎么组织才好用"的推荐做法。
>
> 不是强制协议——Cortex 内部自治，LLM 交互链路可完整替换。
> 这里记录的是经验、理由和推荐默认值，不是规定。
>
> 背景调研见 `docs/research/context-construction/`。

---

## 模型：三块拼成一次调用

每次调用 LLM，上下文由三块拼成：

```
┌─────────────────────────────────┐
│  稳定区  system prompt          │  ← 跨 turn 不变，天然命中缓存
│    规则、人设、工具 schema      │
│    （如有）历史压缩条目         │
├─────────────────────────────────┤
│  帧  当前状态                   │  ← 检查点快照，不是每 turn 重建
│    场景自己决定放什么           │
├─────────────────────────────────┤
│  工作区  本轮产出               │  ← turn 内只追加
│    工具调用与结果               │
│    新到的用户消息               │
└─────────────────────────────────┘
```

**稳定区** 是模型的"记忆底板"——人设、规则、工具定义。它极少变化，天然享受前缀缓存。如果历史攒够了做过一次压缩，压缩条目也放在这里（作为独立 user message 追加在 system 之后），因为它在两次压缩之间不变。

**帧** 是"此刻世界长什么样"。它是**检查点快照**：只在检查点（focus 切换、上下文压缩、重启恢复）时重建，不是每个 turn 开始时整块重建。不同场景放的东西完全不同：

| 场景          | 帧里大概放什么                                          |
| ------------- | ------------------------------------------------------- |
| 日常对话      | 所在频道、参与者、近期历史（固定窗口 + 可选的检索增强） |
| 游戏 / 具身   | 坐标、血量、库存、周围实体、进行中的任务                |
| 长时编程      | workspace 状态、当前 diff、测试结果                     |
| 研究          | 当前 query、检索到的文档片段、已有结论                  |
| 自发 / rhythm | 目标、承诺、上次行动结果、冷却状态                      |

框架不规定帧的内容和大小。这是 Cortex 开发者最主要的设计自由度。

**工作区** 是这一轮 turn 里产生的所有东西——模型的工具调用、工具返回结果、中途到来的新消息。它只追加、不修改。工作区跨多个 turn 存活，直到下一次检查点时随帧一起重建。

## Turn 生命周期

```
触发（收到消息 / tick / 上一轮请求继续）
    ↓
读取冻结的检查点帧（不是每 turn 重建；无 checkpoint 时冷启动构造）
    ↓
循环（模型思考 → 调工具 → 结果追加 → 模型再想 → ……直到停止）
    ↓
收尾（必要时：剪枝进帧 + 压缩进稳定区，写 checkpoint 后清空工作区）
```

**核心不变式：一个 turn 内，稳定区和帧的字节不变。一切新增只往工作区尾部追加。**

这条规则同时保证了：

- 前缀缓存在 turn 内的每一步都能命中
- "模型当时看到了什么"永远可回答
- 并发安全（同一 turn 内不会有两个地方在写）

turn 结束时，如果工作区超过压缩阈值、或 focus 发生了变化，触发一次重建事务：

1. 当前工作区被**代码剪枝**（reasoning 剔除、tool 对合并、失败原文保留）；
2. 旧帧区两个内容区 + 上一版压缩条目交给压缩器**一次 LLM 调用**，产出新压缩条目；
3. checkpoint 先写入磁盘，**保存成功后**才清空内存工作区。

压缩器或 checkpoint 写入失败时，工作区与旧 checkpoint 全部原样保留，下一次重建重试。

## 经验法则

### 1. 稳定的东西放前面，易变的放后面

前缀缓存是按顺序匹配的——前面的内容不变，后面的才能命中。所以自然的排列是：

> 规则 → 人设 → 工具 schema → 压缩条目 → 帧 → 工作区

不需要公式。直觉就够了：**"这个东西多久变一次？"** 变得越慢的越往前放。

### 2. 工具输出降维时，失败原因保留原文

turn 结束后，工具记录要在检查点重建时从工作区降维进帧区（供下一轮参考）。迁移时降维：

```
工具名 + 参数摘要 + 返回值摘要（成功时可截断）
```

大块成功输出**保留首尾、裁去中间**，插入省略标记（默认单条最多 1000 字符，首尾各 400，可配置）。当前不保留指向原始输出的引用键——如果未来确有回溯需求再增加。

但是——**失败的工具调用必须保留原文级的失败原因**。

原因很简单：如果你把"权限不足，当前用户没有 admin 角色"摘要成"调用失败"，模型下一轮会再试一次，然后再失败，然后再试……

成功的可以摘要；失败的不行。失败判定由代码做（非零退出、schema 校验失败、平台拒绝等），不需要模型自己宣称失败。

### 3. 工具调用和工具结果必须成对处理

只裁调用不裁结果、或只裁结果不裁调用，多数 provider 直接报错。裁剪/压缩时永远成对操作。

### 4. 压缩是批量做的，不是每轮挤掉一条

如果每轮都把帧最老的一条挤出去，那帧的开头每轮都在变——前缀缓存从帧第一条起全部作废。

正确做法：攒够阈值，一次性把旧的批量压缩，结果写入稳定区尾部（替换上一版压缩条目）。两次压缩之间，帧只做追加，前缀稳定。

### 5. Turn 内状态冻结了，但世界在变——用 delta 补

帧在检查点时重建后就不动了。但工具调用可能改变世界（移动了位置、写了文件、扣了血）。模型看到的是"检查点快照 + 之后发生的事"——这个时序是对的，前提是：

**工具结果要说清楚它改变了什么。** 不能只返回"操作成功"，要返回"HP 20 → 4"或"已移动到 (100, 64, -200)"。

如果工具结果做不到自述变化，在 step 边界补一条极小的状态 delta 追加到工作区尾部。

### 6. 上下文越长 ≠ 越好

来自外部研究的实证（Chroma _Context Rot_, 2025）：18 个模型的受控实验表明，退化随长度非线性增加，且不存在普适的"安全长度"。

实践含义：

- 不要因为"万一有用"就把所有历史都塞进去
- 旧的模型错误如果不清理会自我强化（模型会模仿自己之前的错误行为）
- 已经被新快照取代的旧状态应该丢掉，不是留着"给模型参考"

### 7. 跨 turn 缓存是运气，不是保证

不同 provider 的缓存 TTL 不同（5 分钟到 1 小时不等）。如果用户隔了 10 分钟才回你，前缀缓存可能已经过期了。

设计上下文时**不要依赖**跨 turn 缓存命中。把它当作"命中了就赚到"的额外收益，不是"必须命中否则成本爆炸"的前提。

## 各场景速览

以下不是规定，是"如果你不确定怎么开始"的参考起点。

### 日常对话

```
稳定区: 人设 + 规则 + 工具 schema + [压缩条目]
帧:     频道信息 + 参与者 + 近期历史（窗口 + 检索增强）
工作区: 本轮工具调用与结果 + 新到消息
```

帧的历史部分：固定窗口是最简单的起点（最近 N 条）。如果有 embedding 检索能力，可以在窗口之外按相关性召回旧消息或用户画像。v3 的做法是窗口达到 ~80% 容量时触发检索补充。

### 游戏 / 具身

```
稳定区: 世界规则 + 安全策略 + 工具 schema + [压缩条目]
帧:     完整当前状态（检查点快照，不是增量更新）
工作区: 本轮动作 + 动作回执 + 状态 delta
```

帧必须是当前真实状态，不能是"上一帧 + diff"——因为 diff 会累积漂移。工具结果必须自述状态变化（§经验法则 5）。

### 长时编程 / 研究

```
稳定区: 协议 + 约束 + 引用规则 + 工具 schema + [压缩条目]
帧:     当前进度 + 已有结论 + 未解问题 + 检索片段
工作区: 本轮工具轨迹
```

这类场景工具输出通常很长（文件内容、搜索结果）。降维尤为重要——成功的读取类输出只留引用和摘要，完整内容如需回溯可走外部存储。

### 自发行为 / rhythm

```
稳定区: 自主性策略 + 人设
帧:     目标 + 承诺 + 上次行动结果 + 冷却状态
工作区: 通常为空（rhythm tick 很少调工具）
```

关键约束：**无变化的 tick 不应产生帧增量、不应发起 LLM 调用。** 否则就是在烧钱做无意义的自我对话。

## 容易踩的坑

| 坑                       | 为什么是坑                 | 怎么避                                                      |
| ------------------------ | -------------------------- | ----------------------------------------------------------- |
| 把所有历史原文塞进上下文 | 成本线性增长 + context rot | 窗口 + 降维 + 压缩                                          |
| 旧的模型错误留在历史里   | 模型会模仿自己的错误       | 失败 turn 只保留"做了什么→因为什么失败"，不保留错误推理过程 |
| 每轮从帧头部挤掉一条     | 前缀缓存每轮作废           | 攒够再批量压缩                                              |
| 工具结果只说"成功"       | 模型不知道世界变了         | 结果必须自述状态变化                                        |
| 压缩条目放在帧里         | 跟着帧每轮变               | 放在稳定区尾部                                              |
| 只裁工具调用不裁结果     | provider 报错              | 成对处理                                                    |
| 假设跨 turn 缓存一定命中 | TTL 过期后成本突增         | 当作额外收益而非前提                                        |
