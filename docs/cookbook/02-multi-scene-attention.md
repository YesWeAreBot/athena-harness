# 02 · 多场景注意力：主心智模式

> Cortex 开发者参考手册。描述"一个数字生命同时存在于多个场景时，上下文如何组织"的推荐做法。
>
> 前置依赖：先读 [01-context-construction.md](./01-context-construction.md)。
>
> 不是强制协议——Cortex 内部自治，可完整替换。
> 这里记录的是经验、理由和推荐默认值，不是规定。

---

## 问题：一个数字生命同时存在于多个场景

一个 Life 可能同时存在于多个 IM 频道、游戏世界、私聊等。这带来一个根本设计问题：

**LLM 的一次调用中，应该看到哪些场景的信息？**

### 全量聚合：否决

把所有场景的事件混入同一上下文（run-length 块等方式），让模型一次看到所有维度。

否决理由：

- **Token 消耗恐怖**——活跃频道的消息量很大，全部展开不可承受
- **工程复杂度高**——重建帧和块、解决时序、处理多场景的工具结果交织
- **信息干扰**——无关场景的内容影响模型对当前任务的判断质量
- **信息泄露风险**——不同场景（如私聊 vs 群聊）的内容不应交叉影响生成
- **Context rot**——上下文越长，模型退化越严重，且非线性增加

### 完全隔离：不够

每个场景独立维护上下文，彼此不知道对方存在。

不够的理由：

- 群友私聊问话时，需要知道"这个人刚才在群里说了什么"
- 管理员介入时，需要 bot 知道"你刚才在那个群做了什么"
- 同一个人在不同场景的交互应该有连续性，否则产生割裂感
- 因果耦合**不是场景的固有属性**——任意两个场景之间随时可能产生因果关系

### 因果耦合度不可静态预判

曾考虑"按因果耦合度分组"——强因果的场景共享上下文，弱因果的隔离。但因果关系是动态出现的，无法在设计时预判哪些场景会产生关联。因此静态分组不可行。

---

## 模型：主心智

**一个 Life 拥有一个主心智。主心智不属于任何频道，它有自己的全局上下文。**

主心智通过 awareness 感知多个频道的状态，主动选择进入（focus）某个频道。当某个频道被激活后，该频道的消息在帧中展开，进入类似 per-scene 的交互模式。

这不是一种可选的"模式"，而是核心架构设计。

### 生物学基础

人只有一个意识流。你不会同时"完整地"处理两场对话——你总是在一个场景中"在场"，对其他场景保持模糊的背景感知。当有足够强的信号（有人喊你名字、手机震动），注意力才会切换。

映射：

- 主心智 = 意识流
- Focus = 当前注意力焦点
- Awareness = 背景感知（知道其他地方在发生什么，但不知道细节）
- Focus 切换 = 注意力转移

### 与 01 的三块结构的关系

Cookbook 01 的三块模型（稳定区 / 帧 / 工作区）完全适用，无需修改结构。变化的是帧里放什么、帧的重建频率，以及工作区的生命周期。

---

## 帧的构造

帧是"主心智此刻看到的世界"——不是客观世界的全貌，而是经过注意力筛选后的主观觉知。

```
稳定区:
  Life identity + 全局规则 + 工具 schema + 主心智压缩条目

帧:
  ┌─ awareness ────────────────────────────────┐
  │  非 focus 场景的极简通知                    │
  │  （场景名、未读数、最新消息预览、优先级）   │
  └────────────────────────────────────────────┘
  ┌─ focus context ────────────────────────────┐
  │  当前 focus 场景的展开内容                  │
  │  （频道信息、参与者、近期历史）             │
  └────────────────────────────────────────────┘
  ┌─ global state ─────────────────────────────┐
  │  全局承诺与待办                             │
  │  最近的 focus 转移记录                      │
  └────────────────────────────────────────────┘

工作区:
  本次检查点以来的所有事件流
```

### Awareness

每个非 focus 场景在帧中只占极少 token。参考信息：

- 场景名称 / 标识
- 未读消息条数
- 最新一条消息的预览（截断到一两行）
- 是否有高优先级事件（被 @、被提及等）

10 个场景的 awareness 可能也就 200-300 tokens。

**Awareness 也需要筛选——不是所有非 focus 场景都值得出现在帧里。** 推荐策略：

- 只展示有未读消息的场景
- 按最后活跃时间排序，取 top N
- 被 @ 或提及的场景总是展示

### Focus context

当前 focus 场景的完整局部状态。具体内容取决于场景类型（见 01 的场景速览表）。对日常对话场景，通常包含：

- 频道元信息（名称、类型）
- 当前参与者
- 近期消息历史（固定窗口 + 可选检索增强）

### Global state

主心智跨场景的全局信息：

- 尚未完成的承诺（"答应了群 A 的人稍后回复"）
- 最近几次 focus 切换的记录
- 跨场景的待办事项

## 帧的生命周期：检查点语义

**帧不是每 turn 重建的。帧是检查点快照。**

### 为什么不每 turn 重建

大部分 turn 只有 1 个 step（模型回复一句话就结束）。在这种场景下：

- 每 turn 重建帧的计算和 I/O 成本浪费了
- 有缓存写入成本的 provider 上，1 step 的 turn 连写入成本都回不了本
- 帧重建后内容变化 → 前缀缓存从帧开始 miss

### 检查点触发条件

帧在以下时机重建：

| 触发条件          | 原因                                |
| ----------------- | ----------------------------------- |
| Focus 切换        | 帧的 focus context 部分要换成新场景 |
| 上下文压缩完成    | 工作区被清空，降维结果需要写入新帧  |
| 系统重启 / 冷启动 | 内存状态丢失，需要从持久化恢复      |

两次检查点之间，帧完全不变。所有新内容追加到工作区。

### 缓存收益

```
稳定区 + 帧 = 完全稳定的前缀（检查点之间）
```

每个 turn 只是在工作区尾部追加新内容，前面的稳定区 + 帧 + 已有工作区内容全部命中缓存。缓存写入只在检查点时发生一次，之后多个 turn 都在消费这个缓存。

### 帧新鲜度

帧可能是多个 turn 之前的快照。但这不影响正确性——两次检查点之间的所有状态变化都以 delta 形式出现在工作区里。模型看到的是"检查点快照 + 之后的变更流"，时序是对的。

这和 01 的经验法则 5 完全一致：

> 模型看到的是"快照 + 之后发生的事"——这个时序是对的，前提是变化要说清楚改变了什么。

---

## 工作区

工作区是检查点之间持续追加的事件流。它跨越多个 turn，直到下一次检查点时压缩清空。

### 内容

工作区中可以出现：

- 用户消息（当前 focus 场景）
- 模型回复
- 工具调用与结果
- Awareness delta（非 focus 场景的新事件通知）
- 旁路检索结果
- Focus 变更记录
- 新展开的 scene context（turn 内切换 focus 时）

### Turn 分隔

不需要显式的 turn 分隔标记。LLM 消息数组中 assistant message 的 `finishReason: stop` 天然标识 turn 边界。工作区就是按时序排列的消息数组，role 交替自然体现多轮结构。

### 工具结果降维

工具结果延迟降维——原文进入工作区，检查点压缩时统一降维。

理由：turn 内的后续 step 需要看到工具的完整返回值来做决策。只有到了检查点时，旧的工具结果才需要降维。降维规则与 01 一致：成功的可以摘要，失败的保留原文。

### 膨胀控制

工作区会持续增长。通过配置压缩阈值（token 数 / 消息条数）和空闲时间来控制。达到阈值时触发压缩，产生新检查点。

## 主心智的三种能力

### 1. Focus：切换默认情境

语义：**接下来主心智默认在目标场景的情境中思考和行动。**

切换 focus 后获得：

- 目标场景的近期历史
- 目标场景的参与者
- 目标场景的未完成事项
- 目标场景的工具或能力

Focus 切换触发帧重建（检查点）。旧 focus 场景的工作区内容降维后保存到该场景的 session store。

### 2. 旁路读取：不改变 focus 的跨场景查询

语义：**我暂时不进入另一个场景，但我想知道那里的部分情况。**

适用场景：

- 私聊中询问群里的事情
- 当前频道的对话需要参考另一个频道
- 需要判断另一个频道是否值得切换 focus

旁路读取通过工具实现。结果进入当前 turn 的工作区，不改变 focus。

与 focus 的区别：

- 旁路读取 = 主动查看，不改变情境
- Focus 切换 = 改变默认情境，触发检查点

### 3. Awareness delta：轻量通知

语义：**非 focus 场景发生了新事件，以极低 token 成本通知主心智。**

新事件在 step 边界追加到工作区。模型在下一 step 自然看到这些通知，自主决定：

- 继续处理当前事务（忽略）
- 旁路查看对应场景
- 通过工具对对应场景采取有限行动
- 决定切换 focus

通常情况下，事件只追加，不打断。是否改变注意力，由模型决策决定。

## Turn 内部行为

Turn = 一次 `streamText` 调用，内部可有多个 step（多次模型调用）。

### Step delta

帧在 turn 内不变，但模型视野通过工作区追加扩展。新事件以 step delta 进入工作区，下一 step 自然可见。

```
step 1:
  帧 + 工作区[...已有内容, 当前消息]
  → 模型调用 → 工具调用

step 2:
  帧 + 工作区[...已有内容, 当前消息, 工具结果, awareness_delta]
  → 模型再次调用

step 3:
  帧 + 工作区[...已有内容, 当前消息, 工具结果, awareness_delta, 旁路结果]
  → 模型再次调用 → 生成回复
```

### 模型的自主决策

模型在每个 step 可以：

- 继续处理当前 focus 场景的事务
- 对其他场景旁路读取
- 在不切换 focus 的情况下对其他场景采取有限行动
- 决定切换 focus（通常在当前事务完成后）

### 打断

一般不使用 turn 打断机制。`AbortSignal` 保留给致命情况：

- Cortex 被销毁
- 超时
- 用户撤回
- 致命资源错误

普通的新消息到达不应打断 turn，而是作为 step delta 追加。

## 压缩

### Global 压缩：主心智的认知轨迹

主心智的压缩条目记录的是**主心智自身的认知连续性**，不是所有场景的原始历史。

压缩内容包括：

- 跨频道做过什么决策
- 哪些频道存在待办
- 哪些承诺尚未完成
- 最近为什么切换 focus
- 对某个用户或频道形成的跨场景判断

压缩内容不包括：

- 各频道的原始消息
- 各频道的完整对话历史
- 可从 scene session store 恢复的局部信息

### 示例

```
主心智压缩条目：

- 群 A 中正在讨论项目发布，已承诺稍后确认配置。
- 用户 X 在私聊中询问群 A 的讨论内容，已回复摘要。
- 群 B 出现管理员介入，已确认并调整行为。
- 上次从群 A 切换到群 B 是因为管理员请求。
- 群 A 的回复尚未完成，返回时需要继续处理。
```

### Per-scene session store

各场景的局部历史保存在各自的 session store 中：

- Focus 展开时从 store 读取
- Focus 切走时将工作区中该场景的内容降维后写回
- 这是 Cortex 的内部状态，不是 Life 的 memory

### 三层存储的区分

| 层                  | 内容                         | 生命周期                         |
| ------------------- | ---------------------------- | -------------------------------- |
| 主心智压缩条目      | 跨场景认知轨迹               | 随主心智，检查点时更新           |
| Scene session store | 各频道的局部历史             | 随 Cortex，focus 展开/切走时读写 |
| Life memory         | 跨时间、跨 Cortex 的长期经验 | 随 Life，跨重启持续              |

## 否决方案：反射弧

### 概念

反射弧是主心智之外的第二条认知路径——独立于主心智并行运行，使用轻量模型和有限上下文，对非 focus 场景的事件做低级别判断和有限行动。

类比：脊髓反射绕过大脑皮层直接产生动作。在本设计中，反射弧不限于硬编码规则，可以使用轻量模型进行有限决策。

### 为什么本阶段不引入

反射弧最初是为了解决"非 focus 场景的响应延迟"而提出的。但经讨论确认：

1. **减少响应延迟不是产品目标。** 我们要做有自己节奏的数字生命，不是秒回的客服机器人。bot 有时在忙、有时没看到，这是正常的。

2. **主心智已经有能力处理非 focus 事件。** 通过 step delta 感知、旁路读取、选择性回复——这些都在主心智的 turn 内完成。反射弧能做的，主心智通过这些机制也能做。

3. **引入第二个决策主体的复杂度不值得。** 并行运行需要协调机制（避免冲突）、通知机制（互相感知）、能力边界划分，而收益在当前阶段不明确。

4. **"不满足主心智触发条件但也不该无视"的灰色地带，可以直接归为"不回复"。** 这符合数字生命有自己节奏的产品定位。

### 未来可能的引入条件

如果未来出现以下真实需求，可重新评估：

- 主心智完全离线时需要维持最低存在（如系统维护期间）
- 某些场景要求无条件的低延迟确认（如安全相关的自动响应）
- 事件量远超主心智处理带宽，且不回复不可接受

届时反射弧可作为 Cortex 的可选扩展能力引入，而不是从第一天就作为核心架构的一部分。

## 待定事项

以下问题尚未决策，留待后续讨论：

1. **Session store 的形态** — 每个 scene 的局部历史怎么持久化和恢复？focus 展开时从 store 取多少、取什么格式？

2. **Awareness 的数据来源和更新机制** — 谁维护各频道的未读计数和预览？是 Cortex 在内存中维护，还是有独立的服务？

3. **Focus 切换的决策机制** — 什么条件触发切换？纯规则（被 @、超时、优先级阈值）还是也可以由模型通过工具决定？两者如何配合？

4. **旁路读取的 scope policy** — 什么信息可以跨频道读取？私聊内容能被带到群聊上下文吗？谁定义这个边界？

5. **主心智压缩条目的具体格式和触发策略** — 压缩是 LLM 做还是规则做？保留什么、丢弃什么？

6. **与 Athena 现有架构的映射** — 主心智对应 Cortex 的哪个部分？awareness 对应 Nerve 事件的哪一层？session store 是 Cortex 的内部状态还是独立包？

7. **"回复时上下文要是最新的"约束** — 如何保证决定回复时，帧或工作区中的信息反映频道的当前状态，而不是滞后的快照？
